LEFT ALONE, AND WHY

  results/leakage_check4_corpactions.py
      DESCRIPTIVE, NO PASS CONDITION DEFINABLE WITHOUT A DECISION. It lists
      price moves in the uncaught -20% to -35% band where close and adj_close
      disagree -- 2 rows on nifty100, 1 on midcap150, measured 2026-09-21 -- and
      states plainly that their provenance is UNVERIFIED because there is no
      corporate-action dataset in this repository to confirm them against, and
      that no manual NSE lookup was performed. A pass condition needs either
      that dataset or a decision about how many unexplained candidates are
      acceptable. Neither exists, so no verdict was invented.

  topn_centralise_check.py, hash-writing mode
      A BEFORE/AFTER DIFFER, NOT A GATE. One run emits a sha256 per (universe,
      sizing, mode) and nothing else; whether those hashes are right is only
      answerable against a baseline taken before the change under test. Its
      `report <before> <after>` mode DOES have a condition and now carries an
      exit status. No baseline is stored in the tree -- both modes write to /tmp
      -- so this script still cannot be wired into a runner as it stands.

  gate_compare.py
      ALREADY EXITS NON-ZERO and was not touched. It cannot run standalone: it
      needs two positional artefact paths plus --universe, --arm and --since.

  tax_acceptance_check.py, transitional_asserts_check.py
      ALREADY EXIT NON-ZERO on failure. Not touched.

TWO THAT NEEDED CARE

  results/leakage_check2_purge.py IS RED BY CONSTRUCTION AND MUST STAY RED.
      It builds the cut the CALENDAR way while engine_core.score_monthly
      defaults to purge_mode="trading". Its 14 failing months -- 7 on nifty100
      and 7 on midcap150 of 105 each, measured 2026-09-21 -- are the legacy
      defect the trading mode fixed, not a live leak. It was NOT switched to
      trading mode and NOT made to pass. Its header now records that it audits a
      path production does not take, and its verdict names the rule it tested
      before giving the count. A runner that calls it will go red until someone
      decides whether it should test the live rule, both rules, or be retired.
      THE LIVE PURGE RULE IS TESTED BY NO SCRIPT IN THIS TREE.

  results/check_b_exec_timing.py NAMES ITS INPUT AND THAT INPUT'S mtime.
      It reads nautilus/reports/<universe>/v2/fills.csv, which is gitignored and
      holds whatever last wrote it. Its verdict now prints both paths and their
      modification times, because a run of nt_verify or verify_v34_arms at a
      non-production tick regenerates them. Measured 2026-09-21: this session's
      own gate runs had rewritten both at tick 0.01 fixed rather than the
      production 0.05/nse grid, so the verdict describes those runs and says so.
      The known latent profile defect is untouched and its output still names no
      profile.

WHAT IS GATED AND WHAT IS ONLY REPORTED

  validate_topn.py gates the IDENTITY GATE only. Whether TOP_N=12 beat TOP_N=8
  on the pre-registered Sharpe criterion is a TRIAL OUTCOME -- the file says so
  itself -- and a trial that does not come out is a result, not a broken
  repository. Gating it would create pressure to re-run at a changed criterion,
  which the spec forbids.

  validate_breadth_live.py leaves T3, the constant-exposure control, ungated, as
  it already did.

  check_a_close_values.py gates the traded column only. adj_close is outside its
  own [low, high] on 211 rows across both universes, which is the exact
  population canonical_price falls back to the raw close on. Gating it would
  fail the run for a condition the engine is documented to handle.

  check_b_exec_timing.py gates "no fill at a close" and "every fill on the
  trading calendar". It does not gate the 4 fills that differ from the day's
  open by 0.01: the file states no tolerance for that and adjudicates none.
