8. IF THE RETIRED PATH BECOMES A FROZEN ARCHIVE, WHAT IS LOST?
================================================================================
Asked so that the argument AGAINST the split is written down by the person
proposing it. The answer is not nothing. THREE THINGS ARE LOST, AND ONE OF THEM
IS LOAD-BEARING FOR THE LIVE UNIVERSES.

(1) THE TRADING CALENDAR IS A 58 ARTEFACT THAT THE LIVE PATH DEPENDS ON.
    LOAD-BEARING.
    STEP 0, make_trading_calendar.py, derives the NSE trading calendar FROM THE
    58 UNIVERSE'S RAW FILES and writes data/nse_trading_calendar.csv.
    engine_core.build_panel filters every panel by it and refuses to run without
    it -- for mid and n100 as much as for the 58. It exists because 70 of 148
    MidCap150 source files carry rows on NSE holidays, putting 237 phantom dates
    into the mid index, 107 inside the backtest window.

    The FILE survives any freeze; it is an artefact. What is lost is the ability
    to REGENERATE it, and it needs regeneration whenever the price data extends
    past its current coverage -- which is exactly when the live universes' window
    next moves.

    SO A SPLIT CANNOT SIMPLY MOVE STEP 0 TO THE ARCHIVE SIDE. Either STEP 0
    stays in the live path while reading 58 raw data, or the calendar is
    re-derived from a live universe, and re-deriving it from mid is precisely
    what its own docstring rules out. THIS IS THE STRONGEST SINGLE ARGUMENT
    AGAINST THE SPLIT AS PROPOSED and it must be resolved in any spec.

(2) THE RETIRED UNIVERSES' NAUTILUS RECONCILIATION BECOMES UNRUNNABLE.
    STEP 16 exports scores_58.parquet and scores_74.parquet, which nt_verify
    reads to reconcile the retired universes -- currently 1,842 and 1,732 days.
    Frozen, those parquets persist but cannot be regenerated, so the retired
    reconciliations can never be re-run. Whether that matters depends on whether
    a retired universe's reconciliation is ever expected to run again. It is a
    real loss and it is a small one.

(3) THE 58 SCORE PANEL FEEDS RESEARCH SCRIPTS THAT ARE STILL CITED AS
    PROVENANCE.
    v5_expanding.csv is read by validate_sizing.py, param_surface.py,
    experiments/sizing_test.py, validate_breadth.py and several diagnostics.
    Several are the recorded provenance of results this project still quotes.
    The cached panel persists through a freeze; only the ability to rebuild it
    from raw data is lost.

WHAT IS EXPLICITLY NOT LOST, AND WAS EXPECTED TO BE
    THE LEAKAGE CHECKLIST. Re-running STEP 2 looked like the strongest argument
    for keeping the retired path runnable -- an executable leakage and overfit
    audit is exactly the kind of thing artefacts cannot replace. IT IS NOT ONE.
    Six of its ten rows are hardcoded "PASS" literals and three more are
    hardcoded labels; only one is computed (section 7). Freezing it loses a
    printout, not a check.

    THE FOUR INVERSE-VOL VALIDATION GATES in STEP 2 ARE genuinely computed
    (ok1 through ok4) and would stop running. But they run on engine_core.backtest
    against the retired 58, which KNOWN_ISSUES.md records as not covering
    production, so what stops running is a live check on a retired universe
    through an engine that does not ship.

9. JUDGEMENT
================================================================================

THIS IS NOT A PIPELINE. IT IS A LAB NOTEBOOK THAT SOMEONE WIRED TO A main().

The tell is the shape, not any individual defect. A pipeline is a dependency
graph that produces a deliverable; every step exists because something
downstream needs it. Here 13 of 32 steps feed anything, 2 produce a published
figure, and the rest write files into metrics/ that no code and no document has
ever read back. Those were not designed as outputs. They are the residue of
exploratory sessions -- someone wanted to see a decay chart, a per-stock P&L, a
feature dictionary -- and when the question was answered the script stayed and
was appended to main(). Nothing in this project ever removes a step, so
run_all.py is a stratigraphic record of every question anyone has asked.

That explains the defects rather than excusing them. make_stats_both.py drifted
to 12/24 because nothing depends on it, so nothing could notice.
make_cash_series.py kept CASH_Y = 0.06 because it predates the decision to set
cash yield to zero and no test spans it. Five reimplementations of the backtest
exist because each exploratory script needed a book immediately and importing
the engine would have meant reshaping the engine. Every one of these is the same
failure: THE PIPELINE HAS NO CONSUMER THAT WOULD BREAK. That property is what
makes drift invisible, and it is structural rather than a set of bugs.

The second thing, and the one worth acting on: 69% OF THE COMPUTE SERVES
UNIVERSES THAT WERE RETIRED, AND IT IS THAT 69% THAT IS ROTTING. The freeze
policy is CORRECT -- retired numbers must not move -- but it has had an
unintended effect: it converts two-thirds of the pipeline into code that must
never change and is therefore never re-run, never exercised and never checked,
while still executing on every full run and still writing into shared
directories. A frozen ARTEFACT and a frozen SCRIPT THAT KEEPS RUNNING are very
different things. The first is a record; the second is an unmaintained process
with write access.

PROPOSAL, NOT YET ACTED ON: SPLIT RATHER THAN REPAIR.
    run_all.py is trying to be two incompatible things -- the reproducible build
    of the live system, and the archive of how the retired results were produced.
    Those want opposite properties. The live path (build, engine, audit, chart,
    parquet, for n100 and mid, roughly nine steps) should be short, exercised on
    every change, and hold the property that its inputs and outputs are checked.
    The retired path should be frozen AS ARTEFACTS rather than as runnable steps:
    the 58 and 74 numbers already exist on disk and must not move, so re-running
    the scripts that made them buys little and risks much. Making it a
    documented, deliberately-invoked archive command would remove
    make_stats_both.py, the 6% cash yield reaching STEP 13, and two-thirds of the
    surface area in one decision, WITHOUT DELETING A SINGLE RECORD.

    Section 8 is the cost side of that proposal and the calendar dependency in
    8(1) is a genuine obstacle, not a detail.

THE COUNTER-ARGUMENT, AND IT IS A REAL ONE.
    This pipeline has produced results that reconcile on 1,836 of 1,836 days and
    verify against a Nautilus port on 92 of 92 rebalances at zero tolerance on
    share counts. Whatever it looks like, THE LIVE PATH WORKS. The concern
    recorded here is not that it is wrong today. It is that the REASON it is
    right today is that a handful of live scripts get attention, and the
    mechanism that would catch the rest going wrong does not exist.

    A reader who concludes from this document that the numbers are unreliable has
    read it wrong. The published figures are reconciled, ported and verified. What
    is unreliable is the PROCESS AROUND them, and the distinction matters.

    Against the split specifically: it is a large change touching retired
    artefacts, the calendar dependency is unresolved, and a pipeline that works
    is not obviously worth restructuring on aesthetic grounds. make_cash_series.py
    is the strongest evidence that the failure mode is not aesthetic -- it is one
    step away from a published table, and it took a TOP_N audit to find it -- but
    one live instance is one live instance, and it is honest to say so.

NO SPLIT IS PROPOSED FOR EXECUTION HERE. If it happens it gets a spec first,
like everything else in this project.
